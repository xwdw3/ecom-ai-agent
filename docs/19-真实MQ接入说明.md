# 真实 MQ 接入说明（pgmq 式消息队列）

> 2026-10-23 上线。替换原先用 `mq_tasks` 表 pending→consumed 两态模拟的 RocketMQ，升级为**真实消息队列语义**，实现方式与开源 pgmq 相同：队列逻辑收口在 PostgreSQL 函数层，多消费者经 `FOR UPDATE SKIP LOCKED` 原子抢占。

## 为什么不是 RocketMQ/Kafka

- 当前 WorkBuddy 云服务沙箱不提供外部 MQ 中间件，连接器市场无 RocketMQ/RabbitMQ/Kafka 类连接器
- 云 SDK 支持 `db.rpc()`（PostgREST `/rpc/<fn>`）→ 可调用自定义 SQL 函数，这是实现真实队列语义的最优路径
- 保留插拔位：`MQClient` 构造可传 `opts.transport` 替换传输层，未来接 RocketMQ HTTP 代理上层零改动

## 能力（对照 RocketMQ 概念）

| 能力 | 实现 | 说明 |
|---|---|---|
| 原子抢占 | `mq_claim`（FOR UPDATE SKIP LOCKED） | 多消费者并发互斥，一条消息只被一个消费者抢到 |
| at-least-once | 可见性超时 `visibility_deadline` + `mq_reclaim_expired` | 消费者崩溃后消息自动回收重投，handler 需幂等 |
| 重试退避 | `mq_nack` 指数退避（2^attempts 秒，封顶 300s） | 失败自动延后重投，last_error 落库 |
| 死信队列 | attempts ≥ max_attempts → status='dead' | 死信可查可统计 |
| 死信重驱动 | `mq_requeue_dead` | 重置 attempts=0 回到 pending |
| 延迟投递 | `mq_enqueue(p_delay_seconds)` | 定时/延时消息 |
| 僵尸确认防护 | ack/nack 仅对 `claimed_by=本消费者` 生效 | 防止崩溃消费者误确认 |
| 队列统计 | `mq_stats()` | 按 topic 统计 pending/processing/consumed/dead/积压时长 |

## 架构分层

- **数据层**：`mq_tasks` 表（新增 attempts/max_attempts/next_retry_at/visibility_deadline/claimed_by/claimed_at/last_error）+ 7 个 SECURITY DEFINER SQL 函数（见 `tools/mq-functions.sql`），函数逻辑不依赖前端，任何语言/进程都能消费
- **客户端层**：`js/mq.js` MQClient（浏览器+Node 双端）——send/claim/ack/nack/reclaimExpired/requeueDead/stats + 后台消费循环（on(topic, handler) 注册分发）
- **工具层**：`js/tools.js` ServiceGateway `mq` 服务全部动作切换到 rpc；`consumeCollectQueue` 改为抢占→频控复核→发送→ack/nack（发送失败自动进退避重试，超限死信）
- **消费入口（三处）**：
  1. `tools/mq-worker.cjs` 独立消费进程（`--once` 单轮 / `--drain` 清空 / 默认常驻 3s 轮询），含心跳与队列深度打印
  2. 运营台 console.html「消费MQ队列」按钮（人工触发）+ 新增「队列状态」「死信重驱动」按钮
  3. `tools/daily-inspection.cjs` 第 6 步每日自动消费 MQ 积压

## 验证结论

- 真实云库 SQL 冒烟：互斥抢占 / 僵尸 ack 防护 / 退避重试 / 死信 / 重驱动 / 超时回收 / 统计 全部通过
- e2e（tools/mq-e2e.cjs，走 PostgREST rpc 通道）：15 项全 PASS
- 业务闭环：入队催付 → worker 抢占 → 频控复核 → 触达落库（result='MQ消费发送'）→ ack
- 单测：tests/mq.test.mjs 9 项；全量 106 项全绿（unit16+phase2 18+acceptance19+phase3 44+mq 9）
- 浏览器 vm 沙箱加载：mq.js 无全局冲突，链路正常

## 运维要点

- 消费者拉起：`node tools/mq-worker.cjs`（生产建议常驻或由调度器周期执行 `--once`）
- 死信处理：运营台「死信重驱动」或 SQL `SELECT mq_requeue_dead(NULL)`；先排查 last_error
- 积压观测：`SELECT mq_stats()`；oldest_pending_seconds 持续增长说明消费能力不足
- 注意：anon 无 DELETE 权限（P0 收紧），清理测试消息走 owner 通道
- 常用 SQL：入队 `SELECT mq_enqueue('topic','{"k":v}'::jsonb,延迟秒,trace_id,最大尝试)`；抢占 `SELECT * FROM mq_claim(ARRAY['topic'],条数,可见性秒,'消费者')`
